# Interaction Polish — Design

**Date:** 2026-05-09
**Status:** Draft
**Owner:** aleksej.pawlowskij

## Problem

Four small interaction defects across the markdown and colorizer plugins, each individually trivial but cumulatively making the viewer feel rough:

1. **Word-selection on double-click splits at `_` and `-`.** Both plugins use
   `find_word_boundaries` (`runtime/interaction/text_selection.cpp:61`),
   which classifies anything `iswpunct` returns true for as a word break.
   On Windows that includes both `_` and `-`. Result: double-clicking
   inside `foo_bar` selects only `foo` or `bar`; double-clicking inside
   `kebab-case`, `--flag`, or `path/to-file_name.ext` always picks the
   wrong sub-word.

2. **URLs in colorized text aren't clickable.** The colorizer plugin has
   no link infrastructure at all — `colorizer_host_adapter.cpp:724`
   contains the comment *"colorizer has no links or code-block
   boundaries"*, the cursor never changes over a URL, and clicks do
   nothing. Concrete example from a real lockfile:
   ```toml
   wheels = [
       { url = "https://files.pythonhosted.org/packages/.../certifi.whl", ... },
   ]
   ```
   The user can see `https://...` colored as a string but cannot follow
   it without copy-pasting into a browser.

3. **Section-jump links with trailing dashes don't resolve.** Many real
   docs use GitHub-flavoured Markdown's slug rule, which keeps trailing
   hyphens when the heading text ends in whitespace + symbols. Example:
   the heading `## General code formatting [^](#table-of-contents)`
   produces GitHub slug `general-code-formatting-` (with trailing dash),
   so the auto-generated TOC entry is written as
   `- [General code formatting](#general-code-formatting-)`. Our
   `slugify` strips trailing dashes (`runtime/layout/layout_engine.cpp:101`),
   so the stored anchor slug is `general-code-formatting`. Fragment
   `general-code-formatting-` never matches any anchor; click is a no-op.

4. **Links inside heading text emit no interactive spans.**
   `LayoutEngine::layout_heading` (`runtime/layout/layout_engine.cpp:275`)
   builds its own minimal `IDWriteTextLayout` directly from concatenated
   inline text and never calls `create_text_layout`. That's the only
   path that produces `block.spans` (the link rects consumed by
   `InteractionEngine::hit_test`). Headings therefore have empty
   `spans`, so clicks on `[^](#top)` inside `## Style Guide [^](#top)`
   fall through to plain text-selection.

## Goals

- Double-click selects whole identifiers, kebab-case names, and CLI
  flags as one word in both plugins.
- URLs in colorized text are visually marked, hover-cursor-changing,
  and clickable — opening in the system browser via `ShellExecuteW`,
  using the same path the markdown plugin already uses.
- TOC links generated by GitHub-style tooling resolve correctly,
  whether or not they carry a trailing `-`.
- Anchor links written in any common case form (`#Section-Name`,
  `#section-name`, `#section-name-`) all resolve to the same heading.
- Clicks on links *inside* heading text route through the standard
  link-action path.

## Non-Goals

- URL-decoding of percent-escaped fragments (`%20`, `%C3%A9`). Deferred
  — no observed cases in current docs; trivially additive later.
- URL detection in markdown body text outside fenced code blocks.
  md4c already produces `MD_SPAN_A` for autolinks; this spec is about
  the colorizer's missing path.
- Tree-sitter-grammar-driven URL classification (require a grammar to
  tag a `link` scope). Out of scope; the regex approach handles every
  language and the no-grammar fallback uniformly.
- Schemes beyond `http`, `https`, `ftp`, `file`. `mailto:`, `git:`,
  `ssh://` etc. are uncommon enough to defer.
- Smart-selection of compound tokens like `foo.bar.baz` on
  double-click (`.` is *not* added to word characters; selecting `foo`
  out of `foo.txt` must keep working).

## Approach

### §1 — Word boundaries

Tighten `is_word_char` in
`src/runtime/interaction/text_selection.cpp` to treat `_` and `-` as
word characters even though `iswpunct` says otherwise:

```cpp
auto is_word_char = [](wchar_t c) {
    if (c == L'_' || c == L'-') return true;
    return !iswspace(c) && !iswpunct(c);
};
```

Single-file change. The function is called from both plugins, so both
benefit at once.

### §2 — Clickable URLs in the colorizer

Three components:

**(a) URL scanner** — new module
`src/runtime/interaction/url_scanner.{h,cpp}`. API:

```cpp
struct UrlMatch {
    int start;    // wchar offset, inclusive
    int end;      // wchar offset, exclusive
};
std::vector<UrlMatch> scan_urls(std::wstring_view text);
```

Implementation: a hand-rolled linear scan, *not* `std::wregex`
(lookbehind support varies across stdlibs and a manual scan is
faster and more predictable for this shape).

For each position `i` in `text`:
1. If `text[i]` is the start of one of the scheme prefixes
   `http://`, `https://`, `ftp://`, `file://` — case-insensitive —
   AND `i == 0` or `text[i-1]` is not alphanumeric (so we don't
   match inside an identifier like `parsehttp://`),
2. then advance `j = i + scheme_len` and consume characters while
   `text[j]` is not whitespace and not in the set
   `<>"`{}|\\^`,
3. then trim trailing characters in `.,;:!?)]}>` from the captured
   range (so `See https://example.com/page.` doesn't capture the
   period and `(see https://x.org/y)` doesn't capture the closing
   paren),
4. emit `UrlMatch{ i, j }` and continue scanning at `j`.

Schemes covered: `http`, `https`, `ftp`, `file`. Same set the markdown
plugin's existing link path already accepts.

The scanner is grammar-agnostic and runs on raw source text. It works
identically for the colorizer's no-grammar fallback (plain text
files), TOML lockfiles, JSON, YAML, comments in C++ — anywhere a URL
literal might appear.

**(b) Layout integration** — in
`src/plugin_colorizer/layout/colorizer_layout.cpp`, after producing
the per-line color spans:

1. Run `scan_urls` once per line during layout (the colorizer is
   already line-oriented; per-line keeps offsets local and avoids
   tracking a second offset basis). Skip the call entirely if the
   line contains no `:` byte — cheap pre-filter.
2. For each match, use `IDWriteTextLayout::HitTestTextRange` to get
   one or more `DWRITE_HIT_TEST_METRICS` rects covering the range.
3. Push each rect as
   `InteractiveSpan{ LinkTarget{ ExternalUrl, url, L"" }, rect }`
   onto the block's `spans` vector (already exists on `LayoutBlock`,
   currently unused by the colorizer).
4. Visual treatment: extend the existing color-span list with one
   range per URL that overrides foreground to `palette.link` and sets
   the underline modifier (`MOD_UNDERLINE`). Render path already
   honours both via `paint_text_runs`.

**(c) Host adapter wiring** — in
`src/plugin_colorizer/window/colorizer_host_adapter.cpp`:

1. After layout, instantiate
   `vs->interaction = std::make_unique<InteractionEngine>(*vs->layout)`
   (struct already has the field; today it's never assigned).
2. In `WM_MOUSEMOVE`, before the existing text-selection cursor
   handling, call `vs->interaction->hit_test(doc_x, doc_y)`; on hit,
   `SetCursor(LoadCursor(nullptr, IDC_HAND))` and short-circuit.
3. In `WM_LBUTTONDOWN`, before the text-selection drag start, repeat
   the hit-test; on hit, `vs->interaction->resolve(...)` and dispatch.
   The colorizer only ever sees `ExternalUrl` targets, so it doesn't
   need the full md-plugin dispatcher. Extract just that branch as a
   small free function in a new header `runtime/host/link_actions.h`:
   ```cpp
   // Opens an external URL via ShellExecuteW; logs failure via WLX_TRACE.
   inline void open_external_url(const std::wstring& url);
   ```
   The md plugin's existing `invoke_link_action` calls this for the
   `OpenExternal` branch and keeps its other branches
   (`ScrollToAnchor`, `ReloadDocument`) inline — those reference
   md-plugin-specific `ViewState` members (`scroll_y`,
   `max_scroll_y`, `file_path`, `update_scrollbar`, `load_document`)
   and shouldn't move. The colorizer just calls
   `open_external_url(action.target)` directly when
   `action.action == OpenExternal`.
4. Wire up the `MenuResult::OpenLink` and
   `MenuResult::CopyLinkAddress` cases at line 719-724, which today
   are explicit no-ops with the comment *"colorizer has no links"*.
   `OpenLink` calls `open_external_url`; `CopyLinkAddress` puts the
   URL on the clipboard via the existing copy helper.

### §3 — Anchor fragment matching

Normalize the incoming fragment the same way `slugify` produces
slugs, before comparison. In
`src/runtime/interaction/interaction_engine.cpp`:

```cpp
static std::wstring normalize_fragment(std::wstring s) {
    for (auto& c : s) c = static_cast<wchar_t>(towlower(c));
    while (!s.empty() && s.front() == L'-') s.erase(s.begin());
    while (!s.empty() && s.back()  == L'-') s.pop_back();
    return s;
}

std::optional<float> InteractionEngine::anchor_y(const std::wstring& slug) const {
    std::wstring needle = normalize_fragment(slug);
    for (auto& a : layout_.anchors)
        if (a.slug == needle) return a.y_offset;
    return std::nullopt;
}
```

Stored slugs are already produced by `slugify` (lowercase, dashes
trimmed), so only the *incoming* fragment needs normalization. After
the change, all of `#general-code-formatting`,
`#general-code-formatting-`, `#General-Code-Formatting`, and
`#GENERAL-CODE-FORMATTING-` resolve to the same anchor.

URL-decoding of `%xx` escapes is **not** added in this change (see
Non-Goals).

### §4 — Links inside headings

Refactor `LayoutEngine::layout_heading` to route inline-to-layout
construction through `create_text_layout`, the same path
`layout_paragraph` uses. Heading font size flows in via the format
argument; bold and the H1/H2 bottom rule layer on top after.

The font-size choice has to happen *before* `create_text_layout`
measures, otherwise its returned `tlr.height` and `tlr.spans` rects
are based on body size and stale when overridden. So extend
`create_text_layout` to accept an optional format pointer:

```cpp
TextLayoutResult create_text_layout(
    const std::vector<InlineNode>& inlines,
    float max_width,
    uint32_t default_color,
    IDWriteTextFormat* format = nullptr);  // NEW; nullptr = use body format
```

Internally, when `format` is null it falls back to the existing
`get_body_format(...)` call; otherwise it uses the supplied format.
Paragraph callers pass nothing and behave identically — the only
caller that uses the new parameter is `layout_heading`.

Then `layout_heading` becomes:

1. Build heading format: `auto fmt = get_body_format(kHeadingSizes[level-1])`.
2. Call `create_text_layout(node.inlines, max_width, colors_.heading, fmt.Get())`.
   `tlr.height`, `tlr.spans`, and `tlr.color_ranges` are now all
   computed at heading size — no post-hoc re-measurement needed.
3. Apply `SetFontWeight(DWRITE_FONT_WEIGHT_BOLD, all)` over the full
   range (preserves visual identity; bold widening can shift glyph
   advances slightly, same as today's behaviour).
4. Push the resulting `TextRun` with both `color_ranges` and
   `code_bg_rects` carried through (rare in headings but cheap).
5. Translate `tlr.spans` rects to document coordinates and append to
   `lb.spans` — same offset arithmetic `layout_paragraph` already
   does.
6. Continue producing the anchor as today (slug from inlines, push to
   `result_.anchors`). Slug computation is unchanged — link-text
   inlines still contribute their text to the slug input, which is
   the existing behaviour and the user-visible spec for §3.

`InteractionEngine::hit_test` already iterates `block.spans` for every
block type; once heading blocks have non-empty `spans`, no engine
change is needed.

This also collapses ~30 lines of duplicated layout-building code that
currently lives only in `layout_heading`.

## Architecture impact

No new modules outside the one added file
`runtime/interaction/url_scanner.{h,cpp}` and the lifted
`runtime/host/link_actions.h`. No public ABI change — the
`wlx-listerine-core` C ABI is untouched, since URL detection happens
entirely in the per-plugin layout layer (the colorizer's plugin code,
not the core DLL). Cache layouts are unaffected: spans are a property
of `LayoutBlock`, already cached.

`InteractionEngine`, today a markdown-only type physically located in
`runtime/interaction/`, now serves both plugins. Its constructor and
public API need no changes. `LinkAction::ReloadDocument` is
unreachable in colorizer use; that's fine — the host adapter's
dispatcher already only fires actions it understands.

## Data flow change (additions only)

```
Colorizer:
  source text -> tree-sitter highlight -> color spans
              -> [NEW] url_scanner -> InteractiveSpan + style override
              -> ColorizerLayout (block.spans now populated)
              -> RenderEngine (underline + link color via existing modifiers)
              -> [NEW] InteractionEngine wired into host adapter
                                    -> hit_test -> resolve -> ShellExecuteW

Markdown:
  Document -> LayoutEngine
              -> [CHANGED] layout_heading routes through create_text_layout
                           => block.spans populated for headings
              -> InteractionEngine::hit_test (unchanged)
              -> [CHANGED] anchor_y normalizes fragment before lookup
```

## Testing

**Unit tests (doctest):**

- `find_word_boundaries`: cases for `foo_bar`, `kebab-case`,
  `--flag-name`, `path/to-file_name.ext`, `_leading`, `trailing-`,
  `multi___under___score`. Each verifies the right `[start, end)` for
  every offset inside the token.
- `url_scanner`: positive cases (bare URL, URL in TOML string, URL in
  C-style comment, URL with query string, URL with port, URL inside
  parens), trailing-punctuation trim (`.`, `,`, `)`, `]`, `?`, `!`),
  negative cases (no URL, malformed scheme, scheme inside an
  identifier `myhttp://`).
- `normalize_fragment`: identity on already-normal slugs, lowercase
  conversion, leading-dash strip, trailing-dash strip, both-side
  strip.
- `LayoutEngine::layout_heading` (existing test fixture): assert
  `block.spans.size() == 1` after laying out
  `## Heading [link](#anchor)`; rect is non-empty.

**Visual regression cases** under `test_data/cases/` (existing
infrastructure):

- New `28_heading_with_inline_link.md` containing
  `## Style Guide [^](#table-of-contents)` plus a `# Table of Contents`
  target. Golden Chrome PNG produced once and committed.
- New `colorizer_url_in_toml.toml` with a typical lockfile entry; the
  colorizer's visual harness verifies the URL is underlined and tinted
  with the link color.

**Manual smoke tests** (single tab in TC):

- Open a markdown doc with a generated TOC whose links carry trailing
  `-`. Click each — all jump.
- Open a heading containing `[^](#top)` — clicking the `^` scrolls.
- Open a `uv.lock` / `Cargo.lock`. Hover URL → hand cursor;
  click → browser opens.
- Double-click inside `kebab-case-name` and `snake_case_name` in both
  the markdown plugin (in inline code) and the colorizer.

## Implementation order

1. §1 (word boundaries) — smallest, lowest risk, lands first.
2. §3 (anchor fragment matching) — also small, isolated to one
   function.
3. §4 (heading link spans) — refactor lands before §2 so the
   `create_text_layout`-and-spans pattern is the single source of
   truth before the colorizer adopts the same shape.
4. §2 (colorizer URLs) — biggest piece, builds on the
   `LinkAction` lift-out and the established span pattern.

Each step ships its own commit and passes `tests.exe` plus visual
regression before moving on.

None. Decisions captured under each section above. URL-decoding of
